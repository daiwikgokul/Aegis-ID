A face gets you noticed.
Trust gets you access.

AEGIS·ID pairs facial recognition with a live trust-score engine. Every verification is scored on match consistency, recognition confidence, liveness and image quality — then routed through risk-based adaptive authentication instead of a single pass/fail check.

How verification works

Capture Webcam frames are sampled continuously across the verification window.
Match LBPH recognition compares each face against the trained model.
Liveness A randomized blink, head-motion, or hand-raise challenge confirms a live subject, not a photo or replay.
Decision The trust score decides: grant, request step-up, or deny — with voice confirmation required at higher risk.

Security testing console

Attack Lab

Controlled presentation-attack testing against the exact same authentication pipeline used during normal verification — nothing here is hard-coded or scripted. The signals decide the outcome.

Attack simulation

Upload a photo — the server applies a synthetic degradation approximating the chosen attack type, then scores it. Repeatable, no physical props needed. These are approximations of attack signatures, not real deepfakes or real replay footage — useful for consistent signal testing, not a claim of matching real attack fidelity.

Live attack demonstration

Present an actual printed photo, phone screen, or video to the webcam (or read a phrase for voice attacks) — the real camera/microphone capture goes through the identical scoring pipeline as genuine verification. This is the more convincing demo, since nothing is simulated.

Only scored decisions are logged — a technical capture failure (no face detected, camera unavailable) isn't a genuine access decision, so it's excluded. Lockout is two-tier: 5 denials for the same recognized identity within 2 minutes locks out just that identity for 60s (a grant clears it) — someone else can still verify normally in the meantime. 5 unrecognized attempts in the same window trigger a separate, system-wide cooldown, since those can't be tied to any one enrolled person.

How it works

About AEGIS·ID

A facial identity system that treats verification as a continuous, risk-weighted decision rather than a single yes/no check.

Trust score engine

Every verification window scores five independent signals — match consistency across frames, recognition confidence, blink/motion-based liveness, texture + frequency-domain + patch-consistency spoof resistance, and image sharpness/exposure — and blends them into one 0–100 trust score.

Adaptive authentication

High trust grants access immediately. Medium trust triggers a step-up re-scan that requires completing a randomly chosen live challenge — blink twice, turn your head, or nod — as a hard gate, not just a higher score. Low trust, or no confident match, is denied.

Spoof resistance

Three classical computer-vision checks blend into this factor: LBP texture entropy (real skin has richer micro-texture than a print or screen), an FFT-based moiré check (screen replay introduces frequency-domain interference), and a patch-consistency check — splitting the face into a grid and comparing local noise statistics, the same core idea vision transformers use (tokenizing into patches), done with classical statistics instead of a trained model. A full ViT-based deepfake classifier needs pretrained weights and GPU inference — impractical for a dependency-light local app — so this is the honest, feasible approximation rather than a claim of using an actual transformer.

Enrollment integrity

Verification-time defenses only matter if enrollment itself can't be spoofed. Registering a new user requires completing the same live challenge as step-up, and every captured frame is screened through the spoof-resistance check before it's allowed into the training set — a printed photo or screen held up during enrollment is rejected outright rather than becoming a trusted identity.

Metadata analysis

Checks EXIF data on uploaded files in the Attack Lab — presence of camera Make/Model/timestamp fields, and editing-software tags (Photoshop, GIMP, etc). Deliberately kept separate from the core trust score rather than forced into it: a live webcam frame is a raw pixel array with no file container, so there's genuinely nothing to check on a real live capture. That's the direct answer to "what if the camera is bypassed" — file-based injection is a distinct threat model with its own defense, not something the live pipeline needs to fake a check for.

Voice ID — second factor

An independent biometric factor alongside the face: classical MFCC + Gaussian Mixture Model speaker verification, trained from scratch on each user's own enrollment recording — no pretrained speaker-embedding model, no internet access needed. Enrollment records two takes of a phrase (one trains the model, one calibrates a per-user reference score); verification records a fresh take and scores it relative to that reference.

Attack Lab

A dedicated page for deliberately testing the verifier against printed photos, phone/screen replay, and video loops — either live on camera, or simulated from an uploaded photo with synthetic degradation applied server-side — using the exact same scoring pipeline as a normal verification, with a running scorecard of attempts blocked.

In-browser camera preview

Every capture flow streams the live annotated camera feed — the same bounding boxes and labels the native window shows — into a popup inside the web page itself via MJPEG streaming, so the whole experience stays in the browser.

Built for the Smart India Hackathon as a deepfake-resistant alternative to static photo ID checks — recognition alone can be spoofed, but consistency, liveness, spoof resistance, confidence, and (optionally) voice together are much harder to fake, at enrollment as well as at verification.
